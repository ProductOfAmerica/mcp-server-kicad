# CLAUDE.md

CodeRabbit reads this file as review criteria (its `code_guidelines` default, left on in `.coderabbit.yaml`), so a rule written here is enforced on pull requests, and a stale one misdirects them.

## Commands

```bash
uv sync --frozen --all-extras --dev   # setup (CI uses exactly this)
uv run pytest -v -n auto              # full suite (CI uses -n auto everywhere)
uv run pytest tests/test_cst.py -v    # one file (no -n: worker startup dwarfs the run)
uv run pytest -k test_name            # one test
uv run ruff check .                   # lint
uv run ruff format --check .          # format check (CI enforces)
uv run pyright                        # type check (basic mode)
uv run python mcp_server_kicad/_cst.py  # CST self-check (demo() asserts)
```

Tests that shell out to `kicad-cli` (ERC, DRC, exports) auto-skip when it is not installed; so does the autouse fixture in `tests/conftest.py` that validates every generated `.kicad_sch` and `.kicad_pcb` is parseable by `kicad-cli`. Confirm `kicad-cli` resolves locally (`KICAD_CLI_PATH`, PATH, the macOS app bundle, or the versioned Windows install roots) or a green run proves less than it looks. Even then, a KiCad 9 `kicad-cli` skips KiCad 10 boards (`_cli_can_load_board`), so those are validated only on the macOS and Windows runners. Tests that intentionally write invalid files use `@pytest.mark.no_kicad_validation`.

That validation fixture is what makes the suite slow: it spawns a `kicad-cli` process per generated schematic, ~380 ms each. It is memoised on the file's UUID-normalised digest, so each distinct schematic body is validated once per process rather than once per test (376 spawns -> 186, measured 2026-08-10); `test_validation_memo.py` guards the key against collapsing anything but a UUID. With `-n auto` on top, a full local run went 213 s -> 40 s on 16 cores.

Run a server by hand: `uv run mcp-server-kicad` (stdio), or under the MCP Inspector with `npx @modelcontextprotocol/inspector uv run mcp-server-kicad`. README.md's Inspector command and `.mcp.json` both launch `uvx --from mcp-server-kicad`, which is a PyPI release, not this checkout, so the `kicad` MCP tools in a Claude Code session here do not see local changes.

## Architecture

Five `MCPServer` servers, one module each: `schematic.py`, `pcb.py`, `project.py`, `symbol.py`, `footprint.py`. Each defines its own `mcp` instance and `main()` console script; `server.py` merges all tools into the unified `kicad` server through `_copy_tools`, which reaches into the private `_tool_manager._tools` (no public copy API; `test_tool_annotations.py` depends on the same internals). Every tool passes one of the annotation presets from `_shared.py` (`_READ_ONLY`, `_ADDITIVE`, `_DESTRUCTIVE`, `_EXPORT`) and returns a Pydantic model from `models.py` when it has structured output. The one exception to the presets is `autoroute_pcb`, whose own `_AUTOROUTE` sets `open_world_hint` because it downloads Freerouting. `test_tool_annotations.py` classifies every tool by name, so a new tool needs a row there.

### One parse/write stack: the CST substrate (`_cst.py`)

Stdlib-only, byte-preserving concrete syntax tree for s-expressions. Bytes in, bytes out; `serialize(parse(b)) == b` by construction; malformed input raises instead of being repaired. As of slice 18 every tool's own reads and writes run on it: all `.kicad_sch` reads and writes, all board reads and writes including the `autoroute_pcb` internals, and the symbol/footprint library tools. Two writes are still performed by a subprocess and are outside it (`sym upgrade` and `fp upgrade`, permanently); see the invariant note below. One more design file comes out of a subprocess, as new output rather than an edit: `autoroute_pcb`'s `<stem>_routed.kicad_pcb`, which pcbnew's `SaveBoard` writes in pcbnew's own format while the input board stays untouched. Slice 18 deleted the version guard, so the substrate refuses no file on its format version and every tool's own reads and writes work on both KiCad 9 and KiCad 10 files. What a tool hands to an installed KiCad is another matter: `kicad-cli` (ERC, DRC, exports, jobsets, the library upgrades, `update_pcb_from_schematic`'s netlist export) and pcbnew (`fill_zones`, `autoroute_pcb`) can only work on files that install can load, and neither a KiCad 9 `kicad-cli` nor a KiCad 9 pcbnew can load a KiCad 10 board (both measured; see `_cli_can_load_board` in `tests/conftest.py` and `_require_pcbnew_era` in `pcb.py`). kiutils is a **test-only** dependency (the `dev` extra): it builds fixtures and reads written files back as an independent oracle, and nothing under `mcp_server_kicad` imports it (`test_runtime_imports_no_kiutils` scans for that).

Two helper modules back the subprocess tools. `_freerouting.py` serves `autoroute_pcb` (needs Java; resolves freerouting.jar via `FREEROUTING_JAR` or a cached auto-download) and hosts the shared pcbnew plumbing: `find_pcbnew_python` (`KICAD_PYTHON` first), `pcbnew_major`, and `wx_app_prelude`. `pcb.py` uses `pcbnew_major` to era-preflight `fill_zones` and `autoroute_pcb`: a KiCad 10 board on a pcbnew 9 refuses up front, and a KiCad 9 board routed through pcbnew 10 gets a result warning that the routed copy is KiCad 10 format. `_netlist_import.py` no longer runs under pcbnew: `update_pcb_from_schematic` does the import in-process (`pcb._apply_netlist_cst`) from a `kicad-cli` netlist. The module survives for two reasons: `pcb.py` imports its stdlib-only netlist helpers, and the three pcbnew scripts (`fill_zones`, autoroute's DSN export and SES import) import it BY NAME under pcbnew's interpreter, through `wx_app_prelude`, to reach `_ensure_wx_app`. Renaming it, or importing anything outside the standard library into it (this package included), breaks all three.

The governing invariant (non-negotiable): bytes the user did not ask to change reach the disk unchanged, and an edit that cannot be done correctly is refused with the file intact. It holds for every write this package performs, including the two a subprocess half-performs. `upgrade_symbol_lib` and `upgrade_footprint_lib` stay outside BYTE PRESERVATION permanently, because rewriting the file is the operation the user asked for and closing that would mean reimplementing KiCad's own format migration, but they are no longer outside ATOMICITY: `_upgrade_out_of_place` gives kicad-cli a scratch copy to truncate and lands the result through `_atomic_write`. Each still takes one bounded `.bak`, which is the undo for an upgrade that SUCCEEDED and is a different concern from a write that failed. Per-file, not per-library: an interrupted `.pretty` upgrade leaves some footprints migrated and none damaged. `fill_zones` and `update_pcb_from_schematic` used to be here and are not any more: a subprocess may compute (pcbnew's zone filler, `kicad-cli`'s netlist export) but never writes the user's board, and the tool writes it through the substrate. `docs/adr-cst-substrate.md` is the decision record; read it before touching any write path. Its status log records how each surface reached the substrate, slice by slice, and ends with the migration complete; append to it when a write path changes shape. The bar every slice cleared, and any new write path still has to clear, is a byte-preservation test, the ERC oracle, and the KiCad 10 CI gate.

Rules the ADR encodes that will bite if ignored:

- **CST I/O is bytes-only.** Never read a KiCad file in text mode on a write path; that rewrites CRLFs. Atom text decodes on demand; `set_text` re-encodes through the KiCad-measured escape codec (the only lossy surface).
- **Board net references are version-gated with zero dialect overlap**: emit numeric `(net N)` at or below `_NUMERIC_NET_VERSION_MAX` (20241229, defined in `pcb.py`), quoted `(net "NAME")` above it, and never copy a numeric net reference across versions. KiCad 10 silently rebinds numbers to the wrong net; its boards have no net table, so nets are derived from usage.
- **Board CST cache** (`_open_pcb_cst`): parsed trees cached per resolved path keyed on mtime+size. Writers must pop their cache entry *before* mutating and never reinsert, so an exception mid-edit cannot leave a poisoned tree cached.
- **Every write goes through `_shared._atomic_write`.** A plain `write_bytes` opens with O_TRUNC, so anything that fails part way through leaves the file truncated, which is exactly what the invariant forbids. Measured on NTFS with a concurrent reader before this landed: 345 torn reads out of 800, including reads of zero bytes, against 0 out of 25,529 through the helper. A blocked replace retries briefly and then raises with the file intact; it never falls back to a direct write. `test_every_write_goes_through_atomic_write` scans the source, because a new direct write passes every functional test in the suite. It only sees `.write_bytes`/`.write_text`, so a write performed by an external process is invisible to it, which is exactly why the subprocess writers went unnoticed for so long; the two that remain are named above.
- **The invariant has two halves, enforced in different places.** `_atomic_write` is durability: the bytes arrive whole or not at all. Validity is separate and is enforced at the point of construction, because `(layer banana)` is a perfectly well-formed s-expression and only wrong in KiCad's semantics, so the CST cannot catch it. A value that reaches a *token* position must be checked before the write: against a closed set (`_check_rotation` in `_shared.py`, `_VALID_LABEL_SHAPES`, the `Literal` on `mirror`) or against the document's own table (`_resolve_layer_cst`, whose model is `_resolve_net_cst`). Free text is not in this class; `set_text` escapes it. Patching these one parameter at a time has failed twice, so the regression net is `test_output_validity.py`, which sweeps hostile values off the live signatures, and the autouse `kicad-cli` oracle in `conftest.py`, which covers boards as well as schematics.
- **Every read goes through `_shared._read_kicad_bytes` (or `_require_kicad_path` when the file goes to `kicad-cli` or pcbnew unread), and every output directory through `_ensure_dir`.** A tool's error message is the whole interface when something goes wrong, and a raw `FileNotFoundError` names neither the tool nor the parameter. Two messages, not one: a missing file says "not found: {path}", while an empty path says "none is configured" and points at the host config, because an unset default is not a typo. `_ensure_dir` keeps `mkdir(parents=True)`, so naming a fresh export folder still creates it; only an unreachable *root* (a typo'd drive, a disconnected share) is refused. `test_bad_path_contract.py` exercises every tool off the live registry, because a new tool that opens its file directly passes every other test in the suite.
- **`no_kicad_validation` suppresses that oracle, so reach for it only when the malformed file *is* the subject**, as in `test_cst.py`. Using it to quiet a tool that writes a bad file is how a 45-degree rotation shipped: the test asserted the illegal angle had been written and switched the oracle off so nothing could object.
- New constructs the server emits come from templates harvested from KiCad's own output (or verbatim copies of system-library nodes), not hand-written s-expressions.

### Path and tool resolution (`_shared.py`)

Config priority: explicit tool parameter > `KICAD_SCH_PATH`/`KICAD_PCB_PATH`/`KICAD_SYM_LIB`/`KICAD_FP_LIB`/`KICAD_OUTPUT_DIR` env vars > auto-detect from a single `*.kicad_pro` in cwd (resolved at import time into module constants). `kicad-cli` resolves via `KICAD_CLI_PATH`, then PATH, then the macOS app bundle, then the default Windows install roots (`_KICAD_WIN_DIRS`: Program Files and per-user LOCALAPPDATA, highest version number first); everything else in the install (stock symbol libs, the pcbnew Python used by `fill_zones`/`autoroute_pcb`) derives from the resolved binary's location (`_kicad_root`), unless `KICAD_SYMBOL_DIR` or `KICAD_PYTHON` overrides it. CLI-backed tools are always registered and fail with an actionable message when `kicad-cli` is missing. `_run_cli` also repairs one specific crash: exit `_KICAD_STARTUP_CRASH` (3221225477) means KiCad could not create its data folder, so it retries once with `KICAD_DOCUMENTS_HOME` set to a local path and caches that in `_documents_home`. Gate on the exit code, never the stderr text, which is locale-dependent. Any process that died rather than exited (`_died`: a negative return code, or an NTSTATUS at or above 0xC0000000) raises regardless of `check`, because `check=False` exists for ERC and DRC violation counts, not for a crash; `_run_pcbnew` applies the same rule to the pcbnew scripts.

### Tests

Fixtures in `conftest.py` build schematics/boards through kiutils builders. Byte-diff helpers (`_pure_insertion`, `_span_preserved`, `_confined`) assert CST edits touch only one contiguous span; use them in any new write-path test. `kicad_native_sch` mirrors KiCad's own output format where kiutils' differs; prefer it when testing format fidelity.

The tool count is hard-coded, and tests pin only two copies (`EXPECTED_TOOL_COUNT` in `conftest.py`, the literal in `test_unified_server.py`). Nothing local checks `server.py`'s instructions, README.md (twice), `mcpb/manifest.json`, `skills/using-kicad/SKILL.md`, or `macos-discovery.yml`, which runs only on `main` and `ci/**` pushes, so grep for the old number whenever a tool is added or removed.

### CI

- `ci.yml`: lint + pyright + pytest matrix (3.10-3.14), no KiCad installed. Triggers on `ci/**` pushes too, so preverify branches get the full matrix. Each leg's interpreter comes from setup-uv's `python-version`, which exports `UV_PYTHON` and so outranks the `3.10` in `.python-version`; a step asserts the leg runs the version it is named for. Until 2026-10-01 the matrix used actions/setup-python, which uv ignores, so every leg ran 3.10.
- `kicad-suite.yml`: full suite on Linux with KiCad 9. Runs on PRs and `ci/**` pushes.
- `macos-discovery.yml`: macOS with KiCad 10; the gating KiCad 10 e2e tests live here. Runs only on pushes to `main` and `ci/**`, **not on PR branches**: validate KiCad-10-affecting changes pre-merge by pushing a `ci/**` branch.
- `windows.yml`: Windows, same trigger as the macOS job and the same reason. It installs **KiCad 10** from KiCad's own download at a version pinned in the file, so it is a second KiCad 10 gate alongside macOS and runs the full suite. It is also the only test of the `_KICAD_WIN_DIRS` probe against a real install, since `shutil.which("kicad-cli")` is `None` on the runner. Windows-specific faults have a history of reaching users first, so a green PR says nothing about this platform.
- `release.yml`: manual dispatch, and the whole release. Bumps the version (pyproject, uv.lock, plugin.json, server.json), packs the MCPB bundle, tags a GitHub release with the wheel, sdist and `.mcpb` attached, publishes to PyPI, then publishes to the MCP Registry with `mcp-publisher login github-oidc` (never the interactive device flow: that JWT expires five minutes after issue). Its bump commit is pushed with the default GITHUB_TOKEN, so it triggers no CI runs; zero runs on a bump commit is normal. Registry ownership is proved by the `mcp-name:` token in the README as published on PyPI, and registry metadata is immutable per version, so description fixes need a new release. The registry step runs last and retries, because the registry rejects a package version PyPI is not serving yet. The `0.0.0` versions in `mcpb/manifest.json` and `mcpb/pyproject.toml` are placeholders the release stamps and never commits; do not bump them by hand.

New files are stamped with the KiCad 9 formats the templates were harvested at (`KICAD_SCH_VERSION = 20250114` in conftest; `_EMPTY_SCH_TPL` in `project.py`, `_SYM_LIB_TPL` in `symbol.py`, `_EMPTY_PCB_TPL` in `pcb.py`, the last harvested from `pcbnew.NewBoard` itself and asserted byte-identical to that harvest). Editing an existing file through the CST never changes its version stamp, so a KiCad 10 file stays KiCad 10, and as of the netlist-import migration that holds for every board this package edits. The two library upgrades are the only exception left and they exist to change the format.

### This repo is also a Claude Code plugin

`.claude-plugin/`, `skills/` (six design skills), `agents/` (reviewer subagents), and `hooks/` ship to plugin users. `hooks/hooks.json` blocks Read/Write/Edit on KiCad file extensions at the harness level, so file manipulation must go through the MCP tools. Its SessionStart hook injects all of `skills/using-kicad/SKILL.md` into every plugin session, so every line of that file is context each plugin user pays for. Changes under `skills/` and `agents/` are user-facing product, not internal docs. `test_skill_tool_coverage.py` fails unless every tool is named in backticks in some `SKILL.md`; `test_skills.py` pins the skill, hook and agent structure and keeps `plugin.json`'s version equal to pyproject's.
